## 一、场景概述

### 1.1 场景定位

在银行系统开发管理中，**功能点估算专家（bank-tech-estimator）** 依据 NESMA/IFPUG 国际标准，对需求文档进行功能点分析（Function Point Analysis），自动生成可审计的估算报告。

### 1.2 核心能力

| 能力 | 说明 |
|------|------|
| 实体识别 | 从需求/设计文档中识别 ILF、EIF、EI、EO、EQ 五类功能点 |
| 复杂度判定 | 依据 NESMA 权重矩阵对每类功能点分 Low/Average/High 三档 |
| 人月换算 | UFP × VAF(银行复杂系数) → AFP → 参考历史基准换算人月 |
| 技术合规审查 | 审查 Java 21/Spring Boot 3 等技术栈的银行安全红线 |
| 审计报告输出 | 生成标准 Markdown 报告 + JSON 明细表，固化到工作空间 |

### 1.3 场景特征

- **类型**: 纯文件驱动场景（与"需求分析与架构拆解专家"同类）
- **DB 依赖**: 无（不需要数据库连接）
- **新工具**: 不需要（复用现有文件读写工具 + Agent 内置 NESMA 知识）
- **输入**: 工作空间 `inputs/` 目录下的需求文档 + 可选 `estimation_config.json`
- **输出**: `outputs/estimations/` 目录下的 Markdown 报告 + JSON 明细

### 4.2 NESMA 权重矩阵（嵌入 Prompt）

| 类型 | Low | Average | High |
|------|-----|---------|------|
| ILF (内部逻辑文件) | 7 | 10 | 15 |
| EIF (外部接口文件) | 5 | 7 | 10 |
| EI (外部输入) | 3 | 4 | 6 |
| EO (外部输出) | 4 | 5 | 7 |
| EQ (外部查询) | 3 | 4 | 6 |

### 4.3 复杂度判定规则

- **ILF/EIF 复杂度**: 基于 DET（数据元素类型）数量和 RET（记录元素类型）数量
  - Low: DET 1-19 且 RET 1
  - Average: DET 20-50 且 RET 2-5
  - High: DET > 50 或 RET > 5
- **EI/EO/EQ 复杂度**: 基于 DET 数量和 FTR（被引用文件类型）数量
  - Low: DET 1-4 且 FTR 0-1
  - Average: DET 5-15 且 FTR 1-2
  - High: DET > 15 或 FTR > 2

### 4.4 人月换算公式

```
UFP (未调整功能点) = Σ(每类功能点数量 × 对应权重)
VAF (调整系数)    = 从 estimation_config.json 读取，默认 1.15
AFP (最终功能点)  = UFP × VAF
人月              = AFP / 基准生产率

默认基准生产率 = 12.5 FP/人月（行业基准）
```

## 六、风险与注意事项

1. **System Prompt 长度**: NESMA 知识库嵌入 Prompt 会增加 Token 消耗，估算约 +2000 tokens/次。对于功能点估算这类专业场景，知识准确性优先于 Token 成本。
2. **LLM 数学计算**: 大模型在乘法求和上可能出错。Prompt 中强调"列出完整计算过程"以利用 CoT 降低错误率，同时 JSON 输出可供下游系统二次校验。
3. **后续迭代**: PRD 中提到的 `queryHistoricalFpBenchmark`（pgvector 历史基准检索）和 `analyzeDomainEntities`（实体拓扑分析）可在后续版本实现为专属工具，当前版本以 Prompt 内置知识覆盖。
4. **estimation_config.json**: 企业标准系数配置的读取逻辑由 Agent 在运行时通过 `read_file_full` 自主完成，无需额外开发。
