## 1. 场景概述

Aura 智能体平台采用**场景驱动架构**：每个场景 = 一个 System Prompt + 一组工具组合 = 一名领域专家智能体。用户通过切换场景，让同一个大模型切换为不同领域专家，自动调用对应领域的原子工具完成专业任务。

| # | 场景名称 | Slug | 图标 | 状态 | 需要数据库连接 | 排序 |
|---|---------|------|------|------|:---:|:---:|
| 1 | 数据库慢 SQL 性能分析 | `db-slow-query-analyzer` | 🗄️ | ✅ active | 是 | 1 |
| 2 | 系统性能分析专家 | `sys-perf-expert` | 📊 | ✅ active | 否 | 2 |
| 3 | 需求分析与架构拆解专家 | `req-arch-expert` | 📋 | ✅ active | 否 | 3 |
| 4 | 功能点估算专家 | `bank-tech-estimator` | 🏦 | ✅ active | 否 | 4 |
| 5 | 测试分析专家 | `bank-test-analyser` | 🧪 | ✅ active | 否 | 5 |
| 6 | UI 原型契约与自动化校验专家 | `bank-ui-validator` | 🔍 | ✅ active | 否 | 6 |
| 7 | COBOL 核心向 Java 现代架构重构专家 | `bank-cobol-to-java-expert` | 🏗️ | 🚧 planned | 否 | 7 |

## 2. 场景使用方法

### 2.1 在 Web UI 中使用

1. 打开 Aura 主界面，在左侧工具栏找到**场景选择器**（Scene Selector）。
2. 点击展开场景列表，浏览所有可用场景的名称、图标和简介。
3. 点击目标场景卡片，确认切换。系统会自动加载该场景的 System Prompt 和工具组合。
4. 如果场景标注了"需要数据库连接"（如场景 1），需先在**数据库连接面板**中配置目标数据库连接信息，测试连通后再开始对话。
5. 在输入框中输入任务描述，按需使用 `@文件路径` 引用工作空间中的文件，按 Enter 发送。

### 2.2 场景数据结构

每个场景在后端由以下字段定义（参见 [`src/lib/agent/scene-data.ts`](web-aura-next/src/lib/agent/scene-data.ts:5)）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `slug` | string | 场景唯一标识符（URL 安全） |
| `name` | string | 场景中文名称 |
| `description` | string | 一句话描述 |
| `icon` | string | Emoji 图标 |
| `systemPrompt` | string | 完整 System Prompt（注入大模型上下文） |
| `toolWhitelist` | string[] \| null | 工具白名单（null = 全部可用） |
| `requiredInputs` | SceneInput[] | 场景启动时需要用户填写的参数 |
| `dbRequired` | boolean | 是否需要数据库连接 |
| `sortOrder` | number | 排序权重 |
| `status` | "active" \| "planned" | 场景状态 |

### 2.3 种子数据初始化

场景种子数据在服务端启动时自动调用 [`seedScenes()`](web-aura-next/src/lib/db/seed/scenes.ts:987) 写入 `scene_definitions` 表。按 `slug` 去重，已存在的场景不会重复插入。如需修改场景内容，需手动更新数据库或删除后重新启动服务。

## 3. 场景 1：数据库慢 SQL 性能分析

### 3.1 基本信息

| 属性 | 值 |
|------|-----|
| Slug | `db-slow-query-analyzer` |
| 图标 | 🗄️ |
| 需要数据库连接 | **是**（PostgreSQL/MySQL） |
| 输入参数 | `sql_file`：待分析的 SQL 文件路径（可选，留空由 AI 自动抓取慢查询） |
| 状态 | active |

### 3.2 核心能力

连接指定数据库，自主利用数据库工具进行多步诊断——**查表结构 → 抓慢 SQL → 分析执行计划**，最终生成 Markdown 优化报告 + 优化 SQL 脚本（如 `CREATE INDEX`）。

### 3.3 专属工具

| 工具 | 功能 |
|------|------|
| `db_list_slow_queries({ limit? })` | 从数据库系统视图获取最近慢查询列表 |
| `db_get_query_plan({ sql, analyze? })` | 获取 SQL 的 `EXPLAIN` 执行计划（JSON 格式） |
| `db_get_table_schema({ table_name })` | 获取表结构、字段类型、现有索引 |
| `db_execute_query({ sql })` | 执行只读 SQL（仅 `SELECT/SHOW/DESCRIBE/EXPLAIN`） |

### 3.4 安全红线

- **严禁**执行任何修改数据的操作（`UPDATE/DELETE/DROP/TRUNCATE/ALTER`）
- 若需分析写操作语句，使用 `EXPLAIN`（不加 `ANALYZE`）

### 3.5 完整 System Prompt

```
你是一名资深的 PostgreSQL/MySQL 性能诊断专家与高级 DBA。

## 🎯 核心任务
1. 根据用户提供的诊断目标（慢 SQL、存储过程或性能瓶颈描述），自主利用数据库工具进行排查。
2. 你必须通过多步工具调用，从"查表结构 → 抓慢 SQL → 分析执行计划"逐步深入，严禁在没有拿到执行计划的情况下给出肤浅建议。
3. 诊断结束后，将最终的性能诊断与优化方案编写成 Markdown 报告，连同优化 SQL 脚本（如 CREATE INDEX），写入工作空间目录。

## 🚫 行为约束
- 安全红线：严禁执行任何修改数据的操作（UPDATE/DELETE/DROP/TRUNCATE/ALTER）。如果必须分析写操作语句，使用 EXPLAIN（不加 ANALYZE）。
- 只在工具返回结果后才给出分析结论，不要凭空猜测。
- 关注全表扫描（Seq Scan）、文件排序（File Sort）、临时表（Temporary）等性能瓶颈信号。
- 使用中文回复。

## 🔧 可用数据库工具
- db_list_slow_queries({ limit? }) — 从系统视图获取最近慢查询列表
- db_get_query_plan({ sql, analyze? }) — 获取 SQL 的 EXPLAIN 执行计划（JSON 格式）
- db_get_table_schema({ table_name }) — 获取表结构、字段类型、现有索引
- db_execute_query({ sql }) — 执行只读 SQL（仅 SELECT/SHOW/DESCRIBE/EXPLAIN）
```

## 4. 场景 2：系统性能分析专家

### 4.1 基本信息

| 属性 | 值 |
|------|-----|
| Slug | `sys-perf-expert` |
| 图标 | 📊 |
| 需要数据库连接 | 否 |
| 输入参数 | `data_dir`：性能数据所在目录（可选，留空由 AI 自动扫描） |
| 状态 | active |

### 4.2 核心能力

扫描工作空间中用户提供的性能数据目录，读取 CPU、内存、磁盘 I/O、网络、TPS 等监控指标文件（CSV/JSON/TXT），交叉对比"高负载时间段"与"硬件资源水位"，定位瓶颈根因。最终产出 `system_bottleneck_analysis.md` 报告。

### 4.3 分析框架（4 步管道）

1. **扫描**：使用 `list_directory` 扫描数据目录
2. **读取**：使用 `read_file_full` 逐个读取性能数据文件
3. **计算**：若数据量大或格式复杂，使用 `execute_python_code` 进行数据解析和统计
4. **输出**：交叉对比得出结论，使用 `write_text_file` 写入报告

### 4.4 交付物

- `system_bottleneck_analysis.md`：包含数据概览、瓶颈定位（根因分析+证据链）、优化建议（按优先级排序）、容量规划建议

### 4.5 完整 System Prompt

```
你是一名资深的系统性能诊断专家与稳定性架构师。

## 🎯 核心任务
1. 扫描工作空间中用户提供的性能数据目录，读取 CPU、内存、磁盘 I/O、网络、TPS 等监控指标文件（CSV、JSON、TXT 等格式）。
2. 交叉对比"高负载时间段"与"硬件资源水位"：将业务指标（TPS、响应时间）与系统指标（CPU usage、iowait、内存使用率）按时间轴对齐分析。
3. 定位瓶颈根因：明确指出是 CPU 瓶颈、内存不足、磁盘 I/O 饱和、网络延迟还是应用层问题。
4. 诊断结束后，将完整的系统瓶颈根因分析报告写入工作空间文件 system_bottleneck_analysis.md，包含：
   - 数据概览（关键指标摘要）
   - 瓶颈定位（根因分析 + 证据链）
   - 优化建议（按优先级排序）
   - 若数据充分，附带容量规划建议

## 📋 分析框架
- 第一步：使用 list_directory 扫描用户指定的数据目录
- 第二步：使用 read_file_full 逐个读取性能数据文件
- 第三步：若数据量大或格式复杂，使用 execute_python_code 进行数据解析和统计计算
- 第四步：交叉对比得出结论，使用 write_text_file 写入报告

## 🚫 行为约束
- 必须在读完实际数据后才给出分析结论，不要凭空猜测。
- 如果数据不足以定位瓶颈，明确告知用户缺少哪些指标。
- 使用中文回复。
- 报告中的数值必须来自原始数据，不可编造。

## 🔧 可用工具
- list_directory({ dir_path }) — 列出目录内容
- read_file_full({ file_path }) — 读取完整文件
- write_text_file({ file_path, content }) — 写文件
- execute_python_code({ code }) — 执行 Python 进行数据分析
- web_search({ query }) — 搜索技术参考
```

## 6. 场景 4：功能点估算专家

### 6.1 基本信息

| 属性 | 值 |
|------|-----|
| Slug | `bank-tech-estimator` |
| 图标 | 🏦 |
| 需要数据库连接 | 否 |
| 输入参数 | `req_dir`：需求文档所在目录（可选，留空由 AI 自动扫描） |
| 状态 | active |

### 6.2 核心能力

依据 **NESMA/IFPUG** 国际标准对需求文档进行功能点分析（ILF/EIF/EI/EO/EQ 识别 + 复杂度判定 + 权重矩阵计算），自动生成审计级估算报告与技术合规审查意见。内置完整的 NESMA 功能点分析知识库（权重矩阵、复杂度判定规则、人月换算公式）。

### 6.3 NESMA/IFPUG 功能点类型

| 类型 | 全称 | 定义 |
|------|------|------|
| **ILF** | 内部逻辑文件 | 系统内部维护的逻辑主表（如散列BGL账户表、交易流水表） |
| **EIF** | 外部接口文件 | 系统引用但由外部维护的数据/接口（如核心账务系统接口、人行二代支付网关） |
| **EI** | 外部输入 | 向系统输入数据以改变系统状态（如开户、记账触发） |
| **EO** | 外部输出 | 系统向外发送数据，包含派生计算逻辑（如日终对账单生成） |
| **EQ** | 外部查询 | 纯数据检索，不改变系统状态，无派生计算（如余额查询） |

### 6.4 标准功能点权重矩阵

| 类型 | Low | Average | High |
|------|:---:|:---:|:---:|
| ILF（内部逻辑文件） | 7 | 10 | 15 |
| EIF（外部接口文件） | 5 | 7 | 10 |
| EI（外部输入） | 3 | 4 | 6 |
| EO（外部输出） | 4 | 5 | 7 |
| EQ（外部查询） | 3 | 4 | 6 |

### 6.5 人月换算公式

```
UFP（未调整功能点）= Σ(每类功能点数量 × 对应复杂度权重)
VAF（调整系数）= 从 estimation_config.json 读取企业标准系数，若无则默认 1.15
AFP（最终功能点）= UFP × VAF
推荐人月 = AFP / 基准生产率（默认 12.5 FP/人月）
```

### 6.6 工作流程（4 步管道）

| 步骤 | 操作 | 关键工具 |
|:---:|---|------|
| 1 | 扫描输入资产：需求文档目录 + 可选 `estimation_config.json` | `list_directory`, `read_file_full` |
| 2 | 实体与事务识别：提取 ILF/EIF/EI/EO/EQ 并判定复杂度 | LLM 推理 |
| 3 | 计算与校准：套用权重矩阵 → UFP → VAF → AFP → 推荐人月 | LLM 计算 |
| 4 | 固化交付物：Markdown 报告 + JSON 明细 + 可选 Excel | `write_text_file`, `generate_structured_excel` |

### 6.7 交付物

| 文件 | 说明 |
|------|------|
| `outputs/estimations/01_功能点估算报告.md` | 完整 Markdown 报告（含系统边界、功能点明细表、技术评审意见、计算公式附录） |
| `outputs/estimations/02_功能点明细表.json` | 结构化 JSON（含每个功能点的 DET/RET/FTR 数量、复杂度判定依据） |
| Excel 明细表（可选） | 通过 `generate_structured_excel` 生成 |

### 6.8 完整 System Prompt

> 此场景 System Prompt 非常长（约 240 行），包含完整的 NESMA/IFPUG 功能点分析知识库、复杂度判定规则、人月换算公式、Markdown 报告模板、JSON Schema 等。完整内容见源文件 [`scenes.ts`](web-aura-next/src/lib/db/seed/scenes.ts:162)。

## 7. 场景 5：测试分析专家

### 7.1 基本信息

| 属性 | 值 |
|------|-----|
| Slug | `bank-test-analyser` |
| 图标 | 🧪 |
| 需要数据库连接 | 否 |
| 输入参数 | `req_dir`：需求文档所在目录（可选，留空由 AI 自动扫描） |
| 状态 | active |

### 7.2 核心能力

读取功能点明细表（场景 4 产出）与需求文档，自动生成银行合规测试用例集（正向/逆向/异常/性能 4 维度），输出 Excel 用例 + 造数规则 JSON。内置金融级测试设计方法论（等价类划分、边界值分析、状态迁移法、正交试验法）。

### 7.3 测试设计方法论

| 方法 | 说明 |
|------|------|
| **等价类划分法** | 有效等价类（正常金额、正常账户状态）+ 无效等价类（金额为0/负数/超限/特殊字符） |
| **边界值分析法** | 金额边界（0.00、0.01、MAX、MAX+0.01）、账户状态边界、并发边界、时间边界 |
| **状态迁移法** | 账户状态机（正常↔冻结→销户）+ 交易状态机（待记账→锁存→成功/超时冲正→挂账） |
| **正交试验法** | 交易类型 × 账户状态 × 金额区间 × 渠道类型的代表性组合 |

### 7.4 银行特有逆向交易类型

| 类型 | 定义 | 测试要点 |
|------|------|---------|
| **冲正 (Reversal)** | 当日交易撤销 | 自动/手动冲正、冲正幂等、余额正确性 |
| **冲减 (Offset)** | 跨日账务调整 | 金额限制、部分冲减、会计分录平衡 |
| **撤销 (Cancel)** | 未清算交易日切前取消 | 已清算后撤销应失败 |
| **超时冲正** | 长事务断线自动触发 | 超时阈值、冲正时序、挂账处理 |
| **挂账 (Suspense)** | 冲正/对账异常资金暂挂 | 触发条件、解挂流程、超时告警 |
| **调账 (Adjustment)** | 人工/系统账务调整 | 权限校验、审计日志、金额上限 |

### 7.5 工作流程（5 步管道）

| 步骤 | 操作 | 关键工具 |
|:---:|---|------|
| 1 | 扫描输入资产：需求文档 + 优先读取场景 4 产出的 `02_功能点明细表.json` | `list_directory`, `read_file_full` |

## 8. 场景 6：UI 原型契约与自动化校验专家

### 8.1 基本信息

| 属性 | 值 |
|------|-----|
| Slug | `bank-ui-validator` |
| 图标 | 🔍 |
| 需要数据库连接 | 否 |
| 输入参数 | `target_url`：目标系统页面 URL（必填）、`spec_dir`：原型契约文件目录（可选） |
| 状态 | active |

### 8.2 核心能力

读取 `inputs/ui-specs/` 下的原型 JSON 文件，驱动无头浏览器（Playwright）抓取目标系统真实 DOM 文本，将原型契约中的"期望文本"与页面"实际文本"逐一进行语义比对，标记状态（MATCHED / MISSING / TEXT_MISMATCH），判定风险等级（Blocker / Medium / Low），生成银行合规审计报告（Markdown + JSON）。

### 8.3 风险等级判定

| 等级 | 判定标准 | 示例 |
|:---:|---|------|
| **Blocker（阻断）** | 银行合规红线缺失：安全提示文案、资损风险声明、法律责任文本、资金相关按钮缺失 | 页面遗漏了"交易发生资损风险提示" |
| **Medium（中）** | 核心业务文案不一致：按钮话术错误、标签名称与设计稿不符 | "确认转账"误写为"确认提交" |
| **Low（低）** | 非关键文案差异：标点符号、空格、大小写 | 句尾多了个句号 |

### 8.4 银行合规红线（严格模式）

以下类型文本必须**逐字匹配**，不得使用子串匹配或语义等价判断：
- 安全提示文案（如"交易发生资损风险提示"）
- 法律责任声明
- 涉及金额、利率的数字文本
- 用户协议链接文案

### 8.5 工作流程（4 步管道）

| 步骤 | 操作 | 关键工具 |
|:---:|---|------|
| 1 | 解析设计契约：读取 `inputs/ui-specs/` 下原型 JSON + 可选 `env_profile.json` | `list_directory`, `read_file_full` |
| 2 | 驱动沙箱抓取：调用 Playwright 无头浏览器获取真实 DOM 文本 | `execute_playwright_validation` |
| 3 | 语义交叉比对：逐条比对期望文本 vs 实际文本 + 路由校验 | LLM 推理 |
| 4 | 成果固化：审计报告 + 可选 Playwright 脚本 | `save_ui_audit_report`, `write_text_file` |

### 8.6 原型 JSON 标准格式

用户需在 `inputs/ui-specs/` 下准备如下格式的原型契约文件：

```json
{
  "page_name": "转账确认页",
  "expected_title": "核心转账确认交易",
  "expected_route": "/transfer/confirm",
  "required_elements": [
    { "label": "付款账号", "type": "label", "required": true },
    { "label": "收款人姓名", "type": "label", "required": true },
    { "label": "确认转账", "type": "button", "action": "submit" },
    { "label": "请输入起存金额", "type": "input_placeholder" },
    { "label": "交易发生资损风险提示", "type": "validation_message", "severity": "Blocker" }
  ]
}
```

### 8.7 专属工具

| 工具 | 功能 |
|------|------|
| `execute_playwright_validation({ targetUrl, authConfig, waitForSelector })` | 驱动无头浏览器抓取页面真实 DOM 文本与结构 |
| `save_ui_audit_report({ reportTitle, targetEnv, overallVerdict, textElements, routeValidation, ... })` | 格式化输出银行合规审计报告（Markdown + JSON） |

### 8.8 完整 System Prompt

> 此场景 System Prompt 非常长（约 210 行），包含 UI 审计方法论（文本比对规则、风险等级判定、交互元素校验、路由合规性校验）、银行合规红线（严格模式）、环境配置读取指南、审计报告输出规范等。完整内容见源文件 [`scenes.ts`](web-aura-next/src/lib/db/seed/scenes.ts:712)。
