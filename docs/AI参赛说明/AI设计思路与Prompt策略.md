# Aura AI 设计思路与 Prompt 策略

> 本文档记录 Aura 项目从零到一的核心 AI 设计决策、Prompt 工程实践，以及 AI 辅助开发过程中的方法论沉淀。
> 作为参赛"AI 辅助开发"的佐证材料。

---

## 一、核心 AI 设计思路

### 1.1 设计原则：大模型只负责推理，工具层负责执行

这是 Aura 最核心的设计理念。我们明确划分了两条责任边界：

```
┌─────────────────────────────────────────────────┐
│              职责边界                             │
│                                                  │
│  大模型 (DeepSeek)               工具层 (TypeScript) │
│  ─────────────────               ─────────────── │
│  ✅ 理解用户意图                  ✅ 操作文件系统   │
│  ✅ 分析数据、发现问题            ✅ 执行 SQL 查询  │
│  ✅ 规划执行步骤                  ✅ 调用外部 API   │
│  ✅ 生成结构化 JSON 数据          ✅ 物化为文件     │
│  ❌ 绝不直接写文件                ✅ 路径安全校验   │
│  ❌ 绝不直接连数据库              ✅ 超时熔断控制   │
│  ❌ 绝不直接执行命令              ✅ 沙箱隔离       │
└─────────────────────────────────────────────────┘
```

**设计原因**：大模型擅长语义理解与逻辑推理，但不可靠、不确定。文件系统和外部调用需要确定性和安全性，必须由代码层保证。我们将 AI 定位为"大脑"，工具定位为"手和眼睛"——大脑指挥，手眼执行。

### 1.2 工具原子化设计

每个工具只做**一件事**。这不是技术限制，而是设计选择：

```typescript
// ❌ 反模式：缝合怪工具
const analyze_and_save = tool({
  description: '读取文件、分析内容、写入报告',
  // 大模型很难判断这个工具在哪个环节出错了
});

// ✅ Aura 方式：原子化拆分
const read_file = tool({ description: '读取文件内容' });
const execute_analysis = tool({ description: '执行分析逻辑' });
const write_report = tool({ description: '写入分析报告' });
```

原子化的好处：
1. **控制权交给大模型**：LLM 自己决定读什么、分析什么、写哪里
2. **错误隔离**：读文件失败不影响写报告，大模型可以换路径重试
3. **可追踪**：每一步在控制台清晰可见
4. **零耦合**：新增场景只需调用已有原子工具，无需新增工具代码

### 1.3 场景 = System Prompt + 工具组合

7 个专家场景没有写一行专属业务代码，全部通过配置实现：

```typescript
// 场景定义的本质：一段 JSON 配置
{
  slug: "db-expert",
  name: "数据库诊断专家",
  systemPrompt: `
    你是一名资深 DBA 诊断专家。
    你的工作方式是：
    1. 先用 db_get_table_schema 了解表结构
    2. 用 db_list_slow_queries 找到慢查询
    3. 对每个慢查询执行 db_get_query_plan 分析原因
    4. 将诊断结论和优化建议写入 diagnose_report.md
    红线：
    - 只能执行只读查询（db_execute_query 仅允许 SELECT）
    - 绝不可修改任何数据
  `,
  tools: ["db_list_slow_queries", "db_get_query_plan", "db_get_table_schema", "db_execute_query", "write_text_file"],
  toolsBlacklist: [], // 不禁止任何工具
}
```

新增一个场景 = 写一段 System Prompt + 声明工具列表。**零代码，纯配置**。

## 二、Prompt 工程策略

### 2.1 场景专家 System Prompt 设计模式

经过多次迭代，我们沉淀了一套 System Prompt 的 **5 段式结构**：

```
┌─────────────────────────────────────────────┐
│  段 1: 角色设定 (Who am I)                   │
│  "你是一名资深的 XX 专家，拥有 10 年经验..."  │
├─────────────────────────────────────────────┤
│  段 2: 工作流程 (How I work)                 │
│  "你的标准诊断流程是：                        │
│   1. 先了解整体情况                           │
│   2. 逐项深入分析                             │
│   3. 生成诊断报告"                            │
├─────────────────────────────────────────────┤
│  段 3: 可用工具 (What I can use)             │
│  "你可以使用以下工具：..."                    │
├─────────────────────────────────────────────┤
│  段 4: 红线与禁止 (What I must NOT do)       │
│  "绝不可修改数据库数据..."                    │
├─────────────────────────────────────────────┤
│  段 5: 产出规范 (What I must deliver)         │
│  "最终必须生成 XX_report.md 文件..."          │
└─────────────────────────────────────────────┘
```

**关键发现**：段 4（红线）比段 2（流程）更重要。大模型天然倾向于"多做"，必须用否定句式明确约束。

### 2.2 工具参数描述策略

工具的 `description` 和参数的 `.describe()` 是大模型判断何时调用的唯一依据。我们遵循以下策略：

| 策略 | 示例 | 效果 |
|------|------|------|
| **动词开头** | `"获取指定目录下的文件列表"` | 明确动作 |
| **说明适用场景** | `"Agent 用于了解项目结构、查找特定文件"` | 告知何时用 |
| **标注限制** | `"仅允许 SELECT/SHOW/DESCRIBE/EXPLAIN/WITH"` | 防止误用 |
| **给正反例** | `"如 users、public.orders"` | 提示格式 |
| **说明默认值** | `"默认 10，最大 50"` | 避免越界 |

```typescript
// 实际代码示例：db_execute_query 工具的参数描述
{
  name: "sql",
  type: "string",
  required: true,
  description: "只读 SQL 语句（仅允许 SELECT/SHOW/DESCRIBE/EXPLAIN/WITH）",
}
```

### 2.3 ReAct 降级策略

当 Agent 连续工具调用失败时，我们在 System Prompt 中嵌入了"自愈指令"：

```
如果连续 3 次工具调用返回错误：
1. 停止当前策略
2. 向用户汇报已尝试的方法和失败原因
3. 请求用户提供更多信息或切换方案
严禁反复重试同一个失败的操作！
```

配合 AI SDK 的 `maxSteps` 参数（硬限制 20 步），双重保障不会陷入死循环。

### 2.4 记忆注入策略

工作空间长期记忆通过以下方式注入上下文：

```typescript
// 概念代码
const memories = await db.query.workspaceMemories.findMany({
  where: eq(workspaceMemories.workspaceId, workspaceId),
});

const memoryContext = memories
  .map(m => `[${m.category}] ${m.key}: ${m.content}`)
  .join('\n');

const systemPrompt = `
${scene.systemPrompt}

## 当前工作空间上下文 (长期记忆)
${memoryContext}

## 工作空间文件结构
${directoryTree}
`;
```

Agent 在每次对话开始时自动获得工作空间的"历史记忆"和"当前文件布局"，无需用户重复描述。

## 三、AI 辅助开发方法论

### 3.1 开发工作流

整个 Aura 项目采用 **PRD → 实施计划 → AI 编码 → 验证** 的四阶段开发流程：

```mermaid
graph LR
    A[需求讨论] --> B[PRD 文档]
    B --> C[实施计划]
    C --> D[AI 编码]
    D --> E[集成测试]
    E --> F[文档更新]
```

| 阶段 | AI 角色 | 产出物 |
|------|--------|--------|
| PRD | 需求分析师 | `docs/*PRD.md` |
| 实施计划 | 架构师 | `docs/*实施计划.md` |
| AI 编码 | 全栈工程师 | `src/**/*.ts` / `.tsx` |
| 验证 | QA | 运行测试，修复 Bug |

### 3.2 PRD 文档规范

每个功能模块都先写 PRD 文档，再写代码。PRD 是 AI 编码的唯一输入：

```
docs/
├── 通用智能体底座补齐实施计划.md   ← 输入给 AI
├── 工具链补齐PRD.md               ← 上游需求
├── 智能体能力PRD.md               ← 上游需求
├── 权限控制与隔离PRD.md
├── 记忆存储PRD.md
└── ...
```

**PRD 的作用**：
1. 将模糊需求转化为结构化规格
2. 定义验收标准（Done Definition）
3. 作为 AI 编码的上下文输入，避免"我说 A、AI 做 B"

### 3.3 项目规则文件驱动

`.roo/rules/rules.md` 是整个 AI 辅助开发的核心约束文件，定义了：

- 项目目录结构
- 双端架构约定
- API 路径规范
- 工具开发规范
- 数据库规范
- 前端规范

**每次 AI 生成代码时，规则文件自动注入上下文**，确保生成的代码始终符合项目约定。这是保证 AI 辅助开发质量的关键基础设施。

### 3.4 用 Markdown 文档而非代码注释做上下文

我们发现一个关键实践差异：

| 方式 | 效果 |
|------|------|
| 在代码中写 JSDoc 注释 | AI 每次需要读代码才能理解意图 |
| 在 `docs/` 中写 PRD 文档 | AI 可直接读取设计意图，再针对性地生成代码 |

**策略**：设计意图放在 `docs/`，实现细节放在代码注释。两者各司其职。

### 3.5 实际案例：客户端打包 Bug 修复

作为 AI 辅助开发的典型案例：

**问题**：Tauri 客户端登录/注册报错 `<Document...`，状态栏永远显示"已连接"

**AI 辅助诊断过程**：
1. 并行读取 6 个相关文件（`tauri.conf.json`、`main.rs`、`lib.rs`、`build-client-lan.bat`、`api-client.ts`、`双端模式2.0.md`）
2. 交叉对比发现 `window.__AURA_MODE__` 从未被设置（`next.config.ts` 只设置 `process.env`，无 bridge）
3. 同时发现 `auth-context.tsx` 4 处裸 `fetch` 未适配客户端模式

**修复**：2 个文件、31 行代码变更，一次打包成功。

**如果纯人工排查**：需要在 Tauri 中调试 WebView、查看网络请求、分析代码路径，预估 2-4 小时。

## 四、Prompt 策略总结

| 策略 | 核心思想 | 应用位置 |
|------|---------|---------|
| **System Prompt 分层** | 通用底座 Prompt + 场景专属 Prompt 叠加 | `/api/chat` 路由 |
| **5 段式场景 Prompt** | 角色 → 流程 → 工具 → 红线 → 产出 | `scene-data.ts` |
| **禁止 > 建议** | 明确说"不要做什么"比"应该做什么"更有效 | 所有场景 Prompt 的红线段 |
| **工具描述精准化** | 参数描述决定调用准确率 | 所有 `tool()` 定义的 `description` |
| **记忆自动注入** | 每次对话自动获取工作空间历史上下文 | `/api/chat` 前置处理 |
| **文件结构预览** | 每次对话注入当前工作空间目录树 | System Prompt 动态拼接 |
| **ReAct 自愈指令** | 失败时主动降级，避免死循环 | System Prompt + `maxSteps` |
| **PRD 驱动编码** | 先写规格说明，再让 AI 编码 | 全项目工作流 |

---

## 五、为什么这些策略有效

1. **信息密度最大化**：每 100 个 Token 的 System Prompt 携带最大的行为约束信息量
2. **职责分离**：大模型不管"怎么做"（工具实现），只管"做什么"（调用决策）
3. **失败友好**：每个工具都是独立的 try-catch 单元，单点失败不影响整体
4. **渐进式复杂度**：通用底座 → 场景专家 → 用户自定义，三层递进，不被复杂性压垮
5. **AI 自己设计约束**：PRD 文档本质上是"给 AI 看的代码规范"，用结构化 Markdown 替代了口头描述
